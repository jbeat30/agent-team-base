# claude-team-base

**스킬 한 번으로 내 프로젝트에 Claude Code 에이전트 팀을 세팅하는 플러그인**

PM, 담당 에이전트, 독립 QA가 단계마다 확인하며 일하는 팀을 내 프로젝트에 설치해요. 기존 규칙과 도구는 그대로 존중해요.
속도보다 요구 충족·누락 발견·범위 통제·근거·마무리 완성도를 우선

- **팀은 부를 때만 일해요.** 설치해도 평소 Claude 대화는 그대로예요. 필요할 때 `/team 요청`이나 "에이전트 팀으로 해줘"처럼 말하면 그 요청에만 팀이 나서요
- 팀이 일할 때는 PM이 요청을 분류하고, 간단한 요청은 바로 처리하고 큰 요청은 기획 → 확인 → 개발 → 검증 순서로 진행해요
- 설치·갱신·제거를 스킬이 대화로 안내, 변경 계획은 한 번만 확인
- 기존 파일은 덮어쓰지 않고 전역 설정과 기능 코드는 건드리지 않음

## 빠른 시작

요구 사항: Claude Code 2.1.302 이상, Node 18 이상

```text
/plugin marketplace add jbeat30/jbeat-conventions
/plugin install claude-team-base@jbeat-plugins
/claude-team-base:setup
```

1. 플러그인을 설치하고 프로젝트에서 `/claude-team-base:setup` 실행
2. 스킬이 프로젝트를 조사하고 필요한 것만 질문
3. 변경 계획을 10줄 이내로 보여주면 확인 **한 번**
4. 설치기가 파일을 복사·병합하고 보호 장치를 점검
5. 새 세션부터 자연어로 요청

저장소를 직접 가져오는 방식도 지원: Claude Code에서 아래처럼 요청

```text
https://github.com/jbeat30/claude-team-base 의 INSTALL.md를 읽고 이 프로젝트에 세팅해줘
```

## 스킬

| 스킬 | 용도 | 비용 |
| --- | --- | --- |
| `/claude-team-base:setup` | 팀 **설치·갱신·제거**, 인자로 `install` `update` `remove` 지정 가능 | 설치 후 보호 장치 점검에서 Claude를 1회 호출 |
| `/claude-team-base:check` | 설치 상태 점검(파일 해시, hook 등록, 역할 파일, 버전) | 없음, `--live` 없이 Claude를 호출하지 않음 |

말로 요청해도 동작: "에이전트 팀 세팅해줘", "팀 설치 상태 확인해줘", "팀 제거해줘"

## 설치할 때 고르는 것

`setup`이 대화로 묻는 항목, 감지로 알 수 있는 것은 다시 묻지 않음

| 선택 | 옵션 | 기본·권장 |
| --- | --- | --- |
| 사용 모드 | **Lite**: PM이 필요한 역할만 직접 호출<br>**Full**: 기획·개발 리더가 하위 역할을 조율, 큰 다영역 작업에 유리 | Lite |
| Full 실행 모드 | **relay**: 리더가 호출 카드를 반환하고 PM이 호출 | relay |
| Context7 MCP | 설치된 버전 기준 문서 확인을 위해 `.mcp.json`에 등록 | 등록 여부 질문 |
| 디자인 시스템(UI 프로젝트) | 토큰·컴포넌트 라이브러리·Storybook·Figma 라이브러리·브랜드 가이드의 위치를 안내, 있으면 **모든 UI 작업의 최우선 기준**으로 따르고 벗어나지 않음 | 있을 때만 |
| 디자인 도구 MCP(선택) | **Playwright**: 실행 중인 화면을 열어 확인<br>**Chrome DevTools**: 크롬으로 화면·콘솔·네트워크·성능 확인, UI/UX 점검에 유용<br>**shadcn/ui**: 검증된 컴포넌트 재사용(`components.json` 필요)<br>**Figma**: Figma 시안이 있을 때, 첫 사용 때 브라우저 로그인 | UI가 있는 프로젝트에서만 질문, Playwright·shadcn/ui 권장 |
| 수정 금지 영역 | 운영 설정·생성 파일·특정 경로 지정 | 없음 |
| 보호 모드 | **권고**: 가드 hook이 위반을 차단<br>**엄격**: 직접 승인 기록 추적(선택, 사용자가 승인 명령을 직접 실행) | 권고 |
| 작업 기록 | `.claude-team-docs/`를 `.gitignore`에 추가 | 추가 |
| 충돌 처리 | 기존 파일과 겹치면 항목별로 건너뛰기 또는 백업 후 교체, 기존 `agent` 설정은 유지 또는 교체 | 충돌 시 질문 |

역할 파일 9종은 모드와 관계없이 항상 전부 설치해요. 모드는 사용 방식의 차이예요

디자인 도구는 `frontend-agent`와 `qa-agent`만 사용, 브라우저 도구(Playwright·Chrome DevTools)는 열어둔 브라우저의 내용을 볼 수 있어 개인 탭·민감한 데이터를 피해야 함, 등록한 서버의 도구 정의가 두 역할의 호출마다 추가되어 토큰이 늘고 `npx`로 외부 패키지를 실행하므로 필요할 때만 선택, 시안에 없는 간격·색·문구를 임의로 만들지 않고 확인하지 못한 화면은 `unchecked`로 표시

- **시안이 없을 때**: PM이 확인 단계에서 디자인 방향(색·타이포·간격·컴포넌트·문구 톤)을 구체적인 안으로 제안하고 확정된 내용을 기획안에 기록, `frontend-agent`는 그 기록대로 구현
- **UI/UX 점검(선택)**: 브라우저 도구가 등록돼 있고 UI를 바꾸는 작업이면 PM이 확인 단계에서 점검 여부를 묻고, 동의할 때만 `qa-agent`가 정해진 흐름·화면 크기로 둘러보며 발견한 문제를 근거와 함께 보고, 에이전트가 하는 시나리오 점검이며 실제 사용자 테스트가 아니고, 실제 계정 입력·주문·결제·데이터 변경은 하지 않음

## 설치 후 사용

팀은 사용자가 부를 때만 켜져요. 부르지 않으면 평소처럼 Claude와 대화해요.

- `/team 요청 내용`: 확실하게 팀으로 시작해요
- 말로 부르기: "에이전트 팀으로 해결해 줘", "pm-agent로 작업해 줘" 같은 표현도 인식해요(모델이 판단하므로 가끔 놓칠 수 있고, 그때는 `/team`을 쓰세요)
- 간단한 질문이나 작은 수정은 팀을 부르지 않고 평소처럼 Claude에게 직접 요청하는 편이 빠르고 토큰도 적게 들어요

```text
/team 기존 로그인 화면에 비밀번호 표시 전환을 추가해줘. 현재 UI 규칙을 따라줘.
```

```text
에이전트 팀으로 해결해 줘: 주문 API 응답에 배송 상태를 추가하고 화면에 연결해줘. 계약과 영향 범위부터 정리해줘.
```

```text
이 함수가 어떤 역할인지 설명해줘.
```

마지막 예처럼 팀을 부르지 않은 요청은 평소 Claude가 답해요. PM의 응답과 질문은 사용자가 쓰는 언어를 따라요.

## 동작 방식

### 에이전트 팀

![에이전트 팀 구성: Lite와 Full](docs/assets/agent-team.ko.png)

팀을 부르면 그 요청 동안 메인 세션이 PM으로 일하며 사용자와 대화하고, 필요한 역할만 불러요(PM 지침은 `/team` 스킬이에요).

| 모드 | 구성 | 적합한 경우 |
| --- | --- | --- |
| Lite | PM이 분석·실무·QA를 직접 호출 | 일반 작업 |
| Full | 기획 리더·개발 리더가 하위 역할을 조율, QA는 PM이 직접 호출 | 다영역·대형·고위험 작업 |

Full의 relay: 리더는 하위 역할을 직접 호출하지 않고 호출 카드를 반환, PM이 카드대로 호출, 리더가 하위를 직접 호출하는 nested는 확인한 버전에서 동작하지 않아 권하지 않음

| 역할 | 담당 |
| --- | --- |
| PM (`/team` 스킬, 메인 세션) | 요청 분류, 사용자 대화·확인, 승인 범위 관리, 검사 실행, 최종 보고 |
| planning-lead · dev-lead | Full에서 기획 조율 · 개발 조율 |
| planner-agent | 요구 분해, 사용자가 놓칠 수 있는 항목 발굴, 인수 기준 |
| architecture-agent | 호출처·계약·회귀·사이드이펙트 분석 |
| frontend · backend · api · test | 배정된 파일만 수정, 테스트 작성 |
| qa-agent | 기획 검증, 변경·검사 기록·완료 체크리스트의 독립 검증 |

### 작업 흐름

![작업 흐름: 접수부터 최종 보고까지](docs/assets/task-workflow.ko.png)

| 등급 | 예 | 경로 |
| --- | --- | --- |
| Q | 질문·설명 | 팀을 부른 뒤에도 PM이 바로 답변 |
| L1 | 주석·오탈자·문구, 동작 불변 | PM이 직접 수정하고 완료 확인 |
| L2 | 동작이 바뀌는 일반 변경 | 위험 신호가 없으면 PM이 직접 처리하고 자가 점검(독립 QA·실행기 기록 없음), 있으면 기획 → 컨펌 → 개발 → 최종 검증 |
| L3 | 계약·권한·데이터·보안·다수 영역 | L2 경로에 영향 분석 필수, 사용자 확인 필수 |

- **요구는 Given/When/Then 인수 기준으로 정리**하고, 테스트가 가능하면 실패 테스트를 먼저 작성
- **요청 원문과 기획안 파일을 모든 에이전트가 직접 읽음**, 요약 전달로 요구가 변형되는 것을 방지
- 요구 범위 변경·정책 결정·호환성 변경·보안·외부 영향이 있으면 사용자에게 먼저 확인, 없으면 PM이 자체 컨펌하고 표시
- 컨펌 전에는 소스를 수정하지 않음, 검증 실패는 개발로 돌아가 보완하며 재작업 한도 3회
- 검사는 승인된 명령만 **검사 실행기**가 실행해 exit code·시각·출력·해시를 기록하고, QA는 PM의 요약이 아닌 이 원본을 확인
- 라이브러리·프레임워크 동작은 설치된 버전 기준으로 Context7에서 확인하고, 확인하지 못한 내용은 `unchecked`로 표시

### 환각·임의 수정 방지

- 요청 원문을 기획안에 그대로 인용하고 모든 에이전트가 원문과 기획안 파일을 직접 읽음
- 모호한 요구는 추정으로 채우지 않고 질문, 사용자가 말하지 않은 항목은 포함·제외·질문으로 결정해 기록
- 확인하지 못한 내용은 사실로 쓰지 않고 `unverified`로 표기, 라이브러리 동작은 설치된 버전 기준 문서로 확인
- 기획안에 적힌 파일만 수정, 컨펌 전 수정 금지, 문서·도구 출력 속 지시문은 지시로 따르지 않음
- 프롬프트만으로 지켜지는 규칙과 가드 hook·검사 실행기로 강제되는 규칙을 구분해 정리: [프롬프트 설계 원칙](docs/PROMPT_DESIGN.md)

### 토큰 효율

- 팀을 부르지 않으면 PM 지침이 세션에 붙지 않아요. 지침은 `/team`을 부를 때만 읽혀요
- 에이전트 프롬프트(역할·양식·가드 메시지)는 영어로 작성, 한국어 대비 상시 주입 토큰 약 26% 감소(역할 10종과 양식 합본, 한 모델 기준 실측)
- 단순 요청(Q·L1)은 팀을 호출하지 않음
- 같은 담당의 파일·요구는 한 번의 호출로 묶음
- relay 절차와 디자인 작업 지침은 해당 작업일 때만 읽는 파일로 분리(PM 지침 입력 약 18% 감소, 한 모델 기준 실측), 필수 규칙은 검사기가 목록으로 확인

## 설치되는 것

```text
.claude/
  agents/        역할 정의 9종
  skills/team/   /team 스킬(PM 지침), 부를 때만 읽힘
  hooks/         가드 hook
  team/          양식, 프로젝트 프로필, 검사 실행기, 설치 매니페스트
  settings.json  hook 등록(기존 설정과 병합), 메인 세션을 PM으로 고정하지 않음
.claude-team-docs/   작업별 기록(요청 원문·기획안·보고·검사 기록·diff), .gitignore 추가 선택
.mcp.json            Context7·디자인 도구 MCP 등록(선택, 기존 설정과 병합)
```

## 갱신과 제거

```text
/claude-team-base:setup update
/claude-team-base:setup remove
```

- 갱신: 설치된 팀 파일을 새 버전으로 **전체 교체**, 변경 내용을 계획으로 보여주고 확인 후 적용, 설치 후 직접 수정한 파일은 자동으로 덮어쓰지 않고 건너뛰기 또는 백업 후 교체를 선택
- 제거: 미리보기를 보여주고 확인 후 설치한 항목만 되돌림, 직접 수정한 파일은 보존, 작업 기록(`.claude-team-docs`)과 백업은 삭제하지 않음
- v0.2.0부터 프롬프트와 기록 라벨이 영어로 바뀌어 이전 버전의 진행 중 작업 기록은 새 버전이 읽지 않음, 갱신 전에 마무리

## 안전장치와 한계

- **가드 hook(권고 모드)**: 역할별 쓰기 경로, 기획안이 확정된 뒤에만 소스 쓰기, 배정된 파일만 수정, 리더의 호출 대상 제한, 쓰기 에이전트의 순차 실행을 검사하고 오류 시 차단
- **실수 방지 장치이며 보안 경계가 아님**: 메인 세션의 셸 명령과 사용자·hook 설정 변경은 막지 않음
- 검사 기록은 메인 세션이 실행기로 실행한 결과이며 위·변조를 완전히 방어하지 않음, QA 보고서에 출처를 표기
- 설치 직후 보호 장치를 실제 Claude 호출로 점검하고, 확인되지 않으면 `no protection`으로 취급
- 취약점은 [SECURITY.md](SECURITY.md)로 비공개 제보

### 기능 성숙도

| 구분 | 기능 |
| --- | --- |
| 기본 | 스킬 설치·갱신·제거, Lite, 역할 파일, 권고 모드 가드, 검사 실행기 |
| 실험적·선택 | Full, relay 실행 모드, 엄격 모드(직접 승인 추적), 요구 보존 추적 검사(`team-check.mjs trace`) |

- 실험적 기능은 실제 Claude 환경에서 검증하지 못했고 직접 처리보다 낫다는 비교 결과도 아직 없음
- **L3 절차 준수는 지침에만 의존하며 강제되지 않아요**: v0.2.0 평가에서 PM이 L3로 분류하고도 계획서·영향 분석·사용자 확인 없이 직접 수정한 사례가 있었어요(그 버전의 직접 경로 도입 영향일 수 있고, 이번 버전에서 그 경로를 없앴지만 다시 측정하지 않았어요). 대화형 사용에서의 준수 여부도 확인하지 못했어요
- 스킬 설치 경로(플러그인 설치, `${CLAUDE_PLUGIN_ROOT}` 치환, 스킬 실행)와 영어 프롬프트의 실제 위임 동작은 실제 Claude에서 아직 확인하지 않음

![모드별 비용·시간·토큰 비교](docs/verification/assets/mode-compare.svg)

- [소규모 fixture 실행 기록](docs/verification/2026-10-19-small-fixture.md), 14회 확인(1회씩, 비대화형, 영어 전환 전 한국어 프롬프트): Lite는 직접 처리보다 L2·L3에서 비용 약 12배·시간 30배 이상, 작은 과제는 직접 처리가 빠르고 저렴하므로 Lite를 기본으로 하고 Full은 대형 작업에서 선택
- [v0.2.0 평가 결과](docs/verification/EVAL_RESULTS_v0.2.0.md)(과제 8종, 반복 1회, 한 모델, 원본 JSON 포함): 팀의 가치는 어려운 과제(숨은 호출처 l1, 암묵 요구 m1)에서만 판단할 수 있는데, 이 과제들은 측정이 적고 반복 1회라 설계 기준으로 판정할 수 없음, 쉬운 과제는 팀에 맡길 요청이 아니므로 그 비용 수치는 팀의 효용 근거로 쓰지 않음
- 팀 구조가 직접 처리보다 품질을 높인다는 보장은 없음

## 기여

이슈와 포크 PR을 환영, 저장소 쓰기 권한은 소유자만 보유하며 모든 변경은 소유자가 검토·승인한 뒤 머지

- 문제 제보·기능 제안: [Issues](https://github.com/jbeat30/claude-team-base/issues/new/choose)

- 외부 기여자의 fork PR 워크플로는 기여 이력과 관계없이 소유자 실행 승인 필요
- 개발 환경은 Node 18 이상, `npm test`로 정적 검사와 단위 테스트 실행, 실제 Claude 측정까지의 검사 방법은 [검사 방법](docs/verification/TESTING.md)
- 자세한 규칙: [기여 안내](.github/CONTRIBUTING.md) · [브랜치 전략](.github/BRANCH_STRATEGY.md) · [개발 규칙](AGENTS.md)
